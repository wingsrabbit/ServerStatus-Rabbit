## 1. 一句话结论

这是一个轻量级多服务器状态监控系统，服务端和客户端共用一个 Python 镜像，通过启动参数区分角色：

- 服务端负责接收客户端通过原始 TCP 上报的状态数据，保存到内存，并通过 Flask 提供监控页和后台管理页。
- 客户端负责采集 Linux 主机的 CPU、内存、磁盘、网络、负载等信息，以兼容 ServerStatus-Hotaru 的文本 TCP 协议格式持续上报。
- 监控展示页使用 Vue 3 + TypeScript 构建，后台管理页是一个无需编译的单文件 HTML，使用 CDN 版 Vue 3。
- 当前版本的核心特征是：纯内存状态、JSON 文件持久化配置、支持掉线 Webhook、支持 HTTPS 证书申请/上传、支持节点 CRUD、支持主题切换、支持按组展示。
- 当前还没有：历史数据、WebSocket 实时推送、Docker Compose、CSRF Token、多用户权限、2FA、协议升级。

## 3. 项目定位与边界

### 3.1 这个项目是什么

这是一个面向小规模 Linux 节点监控的轻量系统，重点是：

- 简单部署
- 单服务端集中展示
- 节点手动管理
- 数据模型足够轻
- 与原始 ServerStatus-Hotaru 客户端协议兼容

### 3.2 这个项目不是什么

从现有代码判断，它目前不是：

- 一个带历史时序存储的监控平台
- 一个支持复杂权限模型的多租户系统
- 一个带 WebSocket 实时推送的低延迟系统
- 一个具备高级安全基线的企业级控制面
- 一个跨平台客户端系统

### 3.3 当前明确支持的环境

- 服务端：Python 3.12，推荐 Docker 运行
- 客户端：Linux 环境，推荐 Docker 运行，并依赖 /proc、/sys、/host/rootfs 挂载获取宿主机指标
- 前端：浏览器访问，由 Flask 静态托管

### 3.4 当前明确不打算支持的事项

根目录的工程文档中明确排除了以下方向：

- Windows/macOS 客户端支持
- MySQL/Postgres 等多数据库后端
- SSR
- GraphQL API
- Kubernetes 部署

## 5. 实际运行架构

### 5.1 服务端启动流程

默认执行 python app.py 时进入服务端模式，流程如下：

1. 初始化日志
2. 调用 server/config_manager.py 创建并校验 data 目录与 JSON 配置文件
3. 读取 config.json 和 settings.json
4. 根据 config.json 中的 servers 初始化内存状态字典
5. 启动 TCP 服务器线程，默认监听 9192
6. 启动 Flask Web 服务，默认监听 9191，按需再启 443
7. 启动掉线检测线程
8. 如果 HTTPS 已启用，再启动证书续期线程
9. 主线程等待 SIGINT 或 SIGTERM

### 5.2 客户端启动流程

执行 python app.py client --server=... --port=... --user=... --pass=... 时进入客户端模式，流程如下：

1. 建立 TCP 连接到服务端
2. 等待服务端发送 Authentication required:
3. 发送 username:password\n
4. 等待服务端返回认证成功消息
5. 读取服务端告知的连接方式 IPv4 或 IPv6
6. 初始化网络采样器
7. 每轮采集 CPU、内存、交换分区、磁盘、网络速度、累计流量、负载、连接性
8. 使用 update {json}\n 格式持续发送
9. 断线后每 5 秒重连

### 5.3 服务端与客户端的协议事实

当前协议不是 HTTP，不是 WebSocket，而是原始 TCP 文本协议。

认证与会话流程：

1. 服务端先发 Authentication required:
2. 客户端回 username:password
3. 服务端按 config.json 中的 servers 列表逐项查找用户名
4. 密码为明文精确匹配
5. 如果节点 disabled 为 true，会直接拒绝连接
6. 同一用户名只允许一个活跃连接
7. 认证成功后，服务端额外发送 You are connecting via: IPv4 或 IPv6
8. 客户端根据这个结果去探测另一种 IP 协议连通性

### 5.4 监控页数据流

监控页是一个纯前端应用，当前不是推送模式，而是 HTTP 轮询：

- 默认轮询接口：/api/stats
- 轮询间隔：来自 web/status-src/public/config.js，当前为 2 秒
- 标题和副标题先从 public/config.js 读取，再尝试从 /api/settings/ui 覆盖

### 5.5 后台管理页数据流

后台管理页不是单独打包项目，而是一个静态 HTML 文件，运行时由 CDN Vue 接管。它通过 fetch 调后端接口完成：

- 管理员初始化
- 登录/登出
- 节点增删改查
- HTTPS 设置
- Webhook 设置
- UI 设置
- DNS 检测
- 证书上传

后台节点列表在已登录且当前标签为“节点管理”时每 5 秒刷新一次。

### 5.6 告警流

掉线告警由后台线程每 10 秒扫描一次：

- 离线判定阈值来自 settings.json 的 webhook.timeout_seconds
- 最小值 10 秒，最大值 300 秒
- 新掉线节点会触发一次 Webhook
- 已掉线节点恢复上线时，只有之前发过掉线告警，才会触发恢复告警

Webhook 请求体固定为：

```json
{"text": "消息文本"}
```

### 5.7 HTTPS 流

当前 HTTPS 有两种模式：

- letsencrypt：用 certbot standalone 自动申请
- manual：后台上传 cert/key 文件

启动逻辑：

1. 保存/准备证书配置
2. 创建 SSLContext
3. 用 werkzeug.make_server 启动 443
4. 把 Session Cookie 的 Secure 切为 true
5. 管理页访问会从 HTTP 301 跳到 HTTPS

证书续期逻辑：

- 每 12 小时检查一次
- 仅在 HTTPS 已开启且模式为 letsencrypt 时执行
- 续期成功后重启 HTTPS server

### 6.2 config.json

作用：持久化节点列表。

默认值：

```json
{"servers": []}
```

每个 server 对象实际字段：

- username：客户端认证用户名，唯一主键

- host：可选主机名
- location：展示位置
- region：2 位大写区域码
- group：可选分组
- disabled：是否禁用

### 6.3 admin.json

作用：管理员认证状态与 Flask secret_key。

默认结构：

```json
{
  "password_hash": "",
  "secret_key": "",
  "locked": false,
  "fail_count": 0,
  "initialized": false
```

说明：

- password_hash 用 werkzeug.security 生成
- secret_key 首次自动生成 32 字节随机 hex
- 连续输错 10 次密码后 locked 变为 true

## 7. 状态模型与监控指标的真实语义

### 7.1 内存状态结构

server/state.py 里维护一个全局字典 _nodes，大致结构为：

```text
{username: {
  last_seen,
  online,
  alert_sent,
  connected_since,
  data: {
    uptime,
    load,
    memory_total,
    memory_used,
    swap_total,
    swap_used,
    hdd_total,
    hdd_used,
    cpu,
    cpu_cores,
    network_rx,
    network_tx,
    network_in,
    network_out,
    online4,
    online6
  }
}}
```

### 7.2 指标来源

客户端采集项：

- uptime：系统开机时长秒数
- load：一分钟负载
- memory_total / memory_used：KB
- swap_total / swap_used：KB
- hdd_total / hdd_used：MB
- cpu：百分比
- cpu_cores：逻辑核心数
- network_rx / network_tx：当前速度，单位 B/s
- network_in / network_out：累计字节数
- online4 / online6：连通性探测结果

### 7.3 一个很重要的实现细节

虽然客户端会上报 uptime，但服务端在输出 /api/stats 时，实际返回给前端展示的 uptime 不是客户端机器开机时长，而是：

- 当前连接最后上报时间 last_seen
- 减去该连接开始时间 connected_since

也就是说，前端显示的 uptime 本质上是“本次在线会话持续时长”，不是系统真实开机时长。

这点非常关键，因为 README 和用户直觉容易把它理解成系统 uptime，但当前代码并不是这样实现的。

### 7.4 online 的判定方式

- 一个节点只要在离线阈值内有上报，就算在线
- disabled 节点在 /api/stats 中强制显示为离线
- 首次从离线变在线会进入 newly_online 队列，供恢复告警使用

## 8. HTTP 接口与权限模型

### 8.1 公开接口

#### GET /

- 返回监控展示页 index.html

#### GET /<path:filename>

- 返回监控页静态资源
- 如果路径前缀是 admin 或 api，会返回 404，防止误路由

#### GET /api/stats

- 返回监控页所需的全部节点状态
- 无需登录

返回结构：

```json
{
  "servers": [
    {
      "name": "",
      "type": "",
      "host": "",
      "location": "",
      "region": "",
      "group": "",
      "disabled": false,
      "online": false,
      "online4": false,
      "online6": false,
      "uptime": "0",
      "load": 0.0,
      "cpu": 0.0,
      "cpu_cores": 1,
      "network_rx": 0,
      "network_tx": 0,
      "network_in": 0,
      "network_out": 0,
      "memory_total": 0,
      "memory_used": 0,
      "swap_total": 0,
      "swap_used": 0,
      "hdd_total": 0,
      "hdd_used": 0,
      "custom": ""
    }
  ],
  "updated": 0
}
```

#### GET /api/settings/ui

- 返回页面标题和副标题
- 无需登录

### 8.2 后台页面与认证接口

#### GET /admin

- 返回后台管理页
- 若 HTTPS 已启用且当前是 HTTP，会重定向到 https://域名/admin

#### POST /admin/setup

- 首次设置管理员密码
- 成功后自动登录

#### POST /admin/login

- 管理员登录
- 连续失败 10 次后锁定

#### POST /admin/logout

- 清理 Session

#### GET /admin/status

- 返回 initialized、locked、logged_in

### 8.3 节点管理接口

这些接口都要求已登录；其中大部分还要求 HTTPS 开启后必须走 HTTPS。

#### GET /api/servers

- 获取所有节点配置，并额外附带实时在线状态

#### POST /api/servers

- 新增节点
- 会做 username、password、name、type、location、region 的校验
- region 必须是 2 位大写字母
- 成功后返回部署命令模板

#### PUT /api/servers/<username>

- 修改节点信息
- username 不可改
- 如果把 disabled 从 false 改为 true，会主动断开当前 TCP 连接并设置离线

#### DELETE /api/servers/<username>

- 删除节点
- 会断开连接并清理状态

### 8.4 系统设置接口

#### GET /api/dns-check

- 登录后可用
- 只要求登录，不强制 HTTPS
- 返回域名解析到的 IPv4 地址，或“无指向”

#### POST /api/settings/https

- 开关 HTTPS
- 支持 letsencrypt 和 manual 两种模式

#### POST /api/settings/port9191

- 开关 9191 HTTP 端口
- 若 HTTPS 未开，不允许关闭 9191

#### POST /api/settings/ui

- 保存页面标题与副标题

#### GET /api/settings/webhook

- 获取当前 Webhook 配置

#### POST /api/settings/webhook

- 保存当前 Webhook 配置

#### POST /api/settings/webhook/test

- 发送测试 Webhook

#### POST /api/settings/cert-upload

- 上传证书与私钥
- 只要求登录，不强制 HTTPS
- 限制扩展名为 .pem/.crt/.key
- 单文件大小不超过 1MB

### 8.5 Session 与安全事实

当前后台认证模型是：

- Cookie Session
- HttpOnly = true
- SameSite = Lax
- HTTPS 开启后才把 Secure 设为 true
- Session 生命周期为 86400 秒
- 当前没有 CSRF Token 机制

## 9. 各模块源码的真实职责

### 9.1 app.py

项目统一入口：

- 默认服务端模式
- client 子命令进入客户端模式
- 负责线程启动顺序与信号等待

### 9.2 client/collector.py

职责：采集宿主机指标。

关键点：

- 如果检测到 /host/proc 和 /host/sys，会提前设置 psutil 的 procfs/sysfs 路径
- 通过 /host/rootfs 优先读取宿主机磁盘使用量
- 网络速度通过 deque 采样差值计算
- 会过滤 lo、tun、docker、veth、kube 等接口
- IPv4/IPv6 连通性探测默认请求 ipv4.google.com 和 ipv6.google.com 的 80 端口

### 9.3 client/reporter.py

职责：TCP 连接、认证、循环发送、断线重连。

关键点：

- 5 秒重连
- 认证/提示流程严格依赖服务端发文案
- 上报格式是 update JSON 行协议

### 9.4 server/config_manager.py

职责：

- 初始化 data 目录
- 读写 config/admin/settings
- 使用原子写入，防止 JSON 被部分写坏
- 节点 CRUD 的持久化层

关键点：

- JSON 如果损坏，直接拒绝启动
- admin secret_key 首次启动自动生成

### 9.5 server/state.py

职责：

- 全局实时状态字典
- 节点上线/离线状态更新
- stats 输出拼装
- 新上线队列
- 配置热加载时的状态保留与清理

### 9.6 server/tcp_server.py

职责：

- 原始 TCP 监听和协议处理
- 用户认证
- 重复连接拒绝
- 禁用节点的热断开

关键点：

- 使用 IPv6 socket 并关闭 IPV6_V6ONLY，从而同时接受 IPv4/IPv6
- 认证阶段 5 秒超时
- 数据阶段 60 秒超时
- 每个连接一个线程

### 9.7 server/alert.py

职责：

- 离线扫描
- Webhook 格式校验
- 异步发送掉线与恢复通知

关键点：

- 只屏蔽了 localhost 和常见私网主机名/IP 文本，不是完整 SSRF 防线
- 请求体固定为 JSON 的 text 字段

### 9.8 server/https_manager.py

职责：

- certbot 申请
- certbot 续期
- 证书与私钥匹配校验
- SSL 上下文创建

### 9.9 server/web_server.py

这是服务端控制面的核心文件，负责：

- Flask 应用初始化
- 公开监控页路由
- 后台登录与 Session
- 节点管理 API
- HTTPS 开关与端口管理
- Webhook 设置
- UI 标题设置
- 证书上传
- HTTP/HTTPS server 的启动、停止和重启

如果后续改控制面功能，绝大多数都要改它。

### 9.10 recover.py

职责：紧急恢复。

两种模式：

- 默认：重置 settings.json，让 9191 开启、HTTPS 关闭
- --reset-password：解除管理员锁定并随机生成一个 12 位新密码

### 9.11 update.sh

职责：热更新运行中的容器。

它会把以下内容直接 docker cp 到容器里并重启：

- server/
- client/
- app.py
- web/admin/
- recover.py

注意：

- 它不会构建 Vue 监控页
- 只适用于后端和后台管理页的热补丁

## 11. 部署、构建与维护方式

### 11.1 Docker 镜像模型

当前使用单镜像双角色：

- 镜像构建时先用 node:18-slim 编译监控页
- 再进入 python:3.12-slim，安装 certbot 和 requirements.txt
- 把整个项目复制到 /app
- 把前端 dist 复制到 /app/web/status/
- ENTRYPOINT 固定为 python app.py

角色区别通过启动参数决定：

- 不带子命令：服务端
- 带 client 子命令：客户端

### 11.2 服务端推荐运行方式

README 给出的标准方式是：

```bash
docker run -d --restart=always \
  --name ss-server \
  -p 9191:9191 \
  -p 9192:9192 \
  -p 443:443 \
  -p 80:80 \
  -v $(pwd)/data:/app/data \
  serverstatus-rabbit
```

### 11.3 客户端推荐运行方式

```bash
docker run -d --restart=always \
  --pid=host --net=host \
  -v /proc:/host/proc:ro \
  -v /sys:/host/sys:ro \
  -v /:/host/rootfs:ro \
  serverstatus-rabbit client \
  --server=服务端IP \
  --port=9192 \
  --user=节点用户名 \
  --pass=节点密码
```

### 11.4 当前端口含义

- 9191：HTTP 监控页 + 后台
- 9192：客户端 TCP 上报
- 443：HTTPS
- 80：仅 certbot standalone 验证时需要

### 11.5 非 Docker 运行方式

README 也给了非 Docker 方案：

- 服务端：pip install -r requirements.txt，手动构建 web/status-src，并把 dist 拷贝到 web/status
- 客户端：pip install psutil requests，然后执行 python app.py client ...

### 11.6 热更新与重建的边界

当前维护方式分两类：

- 完整重建：涉及 web/status-src 或 Dockerfile 改动时使用
- 热更新：只改后端或 web/admin 时可用 update.sh

这个边界是实际代码决定的，不是文档口号：因为 update.sh 根本不会编译 Vue 监控页。

## 13. 当前真实限制、风险与不一致

这一节非常重要。它不是主观挑刺，而是“当前项目现状”的组成部分。

### 13.1 安全层面的真实情况

- 节点密码明文保存在 data/config.json
- 节点认证通过原始 TCP 明文协议完成，9192 本身没有 TLS
- 后台 Session 没有 CSRF Token 保护
- /api/dns-check 只要求登录，不强制 HTTPS
- /api/settings/cert-upload 只要求登录，不强制 HTTPS
- Webhook URL 校验只挡住最明显的 localhost/私网文本，不是完整 SSRF 防护

### 13.2 产品行为上的真实限制

- 监控页是轮询，不是实时推送
- 实时状态存在内存里，进程重启即丢失
- 没有历史数据，无法看趋势图
- 没有多用户和权限分层
- 没有 Compose 文件

### 13.3 后台可用性层面的缺口

- 后台没有统一 GET /api/settings，因此刷新后无法完整回显 HTTPS/端口真实状态
- 系统设置页更像写入面板，不是完整的设置状态面板

### 13.4 指标语义层面的容易误解点

- 前端展示的 uptime 实际上是“本次连接在线时长”，不是主机真实开机时长

### 13.5 资源与校验之间的不一致

- web/status-src/src/assets/img/client 中除了标准两位区域码 SVG，还存在 pirate.svg、rainbow.svg、trans.svg、EU.svg 等特殊图标
- 但后台/API 的 region 校验只允许 ^[A-Z]{2}$
- 这意味着 pirate、rainbow、trans 这类图标无法通过当前后台正常录入，只能通过绕过校验或直接改配置文件使用

### 13.6 文档与实现的小不一致

- 前端源码子项目仍保留上游 `hotaru_theme` 包名和 `0.4.5` 包版本
- web/status-src/public/config.js 里仍有 footer 配置项，但当前 App.vue / TheFooter.vue 并没有真正使用这个 footer 字段
- web/status-src/public/json/.gitignore 是上游遗留占位，当前前端并不使用静态 stats.json 读取模式，而是直接请求 /api/stats
- web/status-src/.github/workflows/action.yml 明显是上游主题子项目的发布流程，不代表整个根仓库当前的正式发布流水线

### 13.7 测试层面的现实

- 仓库中没有测试目录
- 没有单元测试或集成测试配置
- 现有质量保证主要依赖手工验证、实际部署与简单脚本
